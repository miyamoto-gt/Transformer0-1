## はじめに

前回、自作のTransformer(GPTMini)をtiny_shakespeareで学習させ、val lossを1.83まで下げた。動くものはできた。ただ、こんな疑問が残った。

**もしどこかにバグがあったとして、私はそれに気づけるのか。**

lossが下がっていれば正常と判断していいのか。下がらなかったとき、原因をどう絞り込むのか。前回うまくいったのは「たまたま間違えなかった」だけかもしれない。

そこで今回は**わざと壊す**ことにした。6種類のバグを意図的に仕込み、それぞれがどんな症状として現れるかを記録する。症状から原因を逆引きできる表を作るのが目的である。

結果を先に書く。6つのうち**5つは「val lossを見ていれば安心」という前提が通用しなかった**。うち1つに至っては、バグのあるモデルのほうがlossが47分の1まで下がった。

この記事はその準備編である。壊す前に「正常とは何か」を数値で定義する。

## 基準にするモデル

前回作ったもの(Week2)をそのまま使う。壊す実験なので、比較対象が固定されていることが何より重要になる。

| 項目 | 値 |
|---|---|
| パラメータ数 | 215,873 |
| d_model | 64 |
| 層数 | 4 |
| ヘッド数 | 4 |
| block_size(文脈長) | 128 |
| batch_size | 32 |
| 学習率 | 1e-3(AdamW) |
| 語彙数 V | 65(文字単位) |

データはtiny_shakespeare。先頭90%(約100万文字)をtrain、残り10%(約11万文字)をvalに使う。

```
入力  x : (32, 128)              batch × 文字数(整数ID)
        │
        ├─ tok_emb : Embedding(65, 64)
        └─ pos_emb : Embedding(128, 64)
        ▼
      (32, 128, 64)
        │
      Block × 4     ← Pre-LN + MultiHeadAttention + FFN + 残差
        ▼
      (32, 128, 64)
        │
      最終 LayerNorm → lm_head : Linear(64 → 65)
        ▼
    logits : (32, 128, 65)       各位置で次の文字の予測
```

### seedを固定する理由

`build_model()`の中でseedを固定している。

```python
def build_model():
    torch.manual_seed(1337)
    return GPTMini(V, d_model, block_size, n_layer)
```

比較実験では、条件間で違うのが「壊した1か所」だけである必要がある。seedを固定しなければ初期重みが毎回変わり、出た差が壊し方のせいなのか初期値のせいなのか区別できない。

## 4つの物差し

ここからが本題である。lossの値を見て「良い」「悪い」と判断するには、比較対象が要る。

### 物差し1:ln(V) = 4.174

**何も学習していないモデルのloss**である。

文字の種類は65個。何も知らないモデルは、次の文字を65個すべて同じ確率、つまり1/65と予測するしかない。このとき正解の文字にも1/65しか割り当てていないので、交差エントロピーは`-log(1/65) = log(65) = 4.174`になる。

これが**ゼロ点**になる。

- この値より下 → 何かを学んでいる
- この値より上 → **でたらめより悪い**

### 物差し2:1/V = 0.0154

**一様に予測したときの、最も確率の高い文字の確率**である。65個に均等なら1/65 = 0.0154。

実測値がこれより大きければ、モデルは特定の文字に偏った予測をしている。学習後なら当然だが、**学習前にこれが大きいのは根拠のない自信**を意味する。

### 物差し3:logits std = 0

logitsは、softmaxに入る前の65個の数値である。完全に一様な予測なら65個の値は全部同じ、つまり標準偏差0になる。

これも学習前の状態を診るための指標になる。

### 物差し4:ユニグラム水準 ≈ 3.30

これは**実験の途中で見つけた物差し**である。事前に用意していたものではない。

「文字の出現頻度だけを覚えた状態」のlossにあたる。英語テキストではスペースやeが多く、zやqは稀である。この偏りは前後の文脈と無関係に成り立つので、出力層のバイアスだけで表現できる。

```
logits = x @ weight.T + bias
                        ↑ 入力に関係なく足される定数
```

学習が進むと、スペースのbiasは大きく、zのbiasは小さくなる。理論的には各文字の出現頻度の対数に対応する値へ収束し、そのとき達成されるlossがユニグラムのエントロピーになる。tiny_shakespeareでは約3.30だった。

これが物差しになるのは、**バグのある実験のいくつかが揃ってここで停滞したから**である。第2回で扱う。

### まとめると

```
 4.174  ln(V)        何も知らない
 3.30   ユニグラム    文字の頻度のみ覚えた
 2.24   基準の到達点  文脈依存の規則を学んでいる
 1.83   前回の3000 iter到達点
```

lossが3.3で止まっていたら「頻度しか学べていない」、2.2まで下がっていれば「文脈を使えている」と読める。**数字の絶対値ではなく、どの水準にいるか**で判断できるようになった。

## 学習前のモデルを測る

物差しが揃ったので、学習を始める前のモデルを測る。Karpathyの「A Recipe for Training Neural Networks」にある手順である。

```python
@torch.no_grad()
def measure_init(m):
    m.eval()
    losses = torch.zeros(eval_iters)
    stds   = torch.zeros(eval_iters)
    maxps  = torch.zeros(eval_iters)
    for k in range(eval_iters):
        x, y = get_batch(val, block_size, batch_size)
        logits, loss = m(x, y)
        losses[k] = loss.item()
        stds[k]   = logits.std().item()
        maxps[k]  = logits.softmax(-1).max(-1).values.mean().item()
    m.train()
    return losses.mean().item(), stds.mean().item(), maxps.mean().item()
```

結果。

```
init loss     : 4.3254   (ln(V) = 4.1744)
logits std    : 0.5767
max prob mean : 0.0522   (1/V = 0.0154)
```

3つとも一様の状態から外れた。

| 測定値 | 実測 | 一様のとき | 差 |
|---|---|---|---|
| init loss | 4.3254 | 4.1744 | **+0.151** |
| logits std | 0.5767 | 0 | **+0.577** |
| max prob | 0.0522 | 0.0154 | **3.4倍** |

**学習前のモデルが、でたらめより悪い予測をしている。**

最も確率の高い文字に5.22%を割り当てていた。一様なら1.54%なので3.4倍である。何も学習していないのに、根拠なく「たぶんこの文字だ」と主張している状態になる。

### 原因は出力層の初期化にある

PyTorchの`nn.Linear`の既定初期化がそのまま出たものと考えられる。

`lm_head`は`Linear(64, 65)`である。PyTorchはこの重みを`U(-1/√64, +1/√64)`、つまり±0.125の一様分布から初期化する。64次元の入力との内積を取るので、出力にはそれなりのばらつきが生まれる。結果としてlogitsのstdが0.577になり、一様からずれる。

### 学習曲線に現れる

このずれは曲線の形にそのまま出た。

![基準モデルの学習曲線](/images/w3/standard.png)

最初の25 iterで4.33から3.12へ、1.2以上落ちている。そのあとは緩やかになる。序盤のこの急降下は、言語のパターンを学んでいるというより、**根拠のない自信を引き下げる作業**だと考えられる。

灰色の点線がln(V) = 4.174である。**始点が点線の上にある。** 学習開始時点では、でたらめに予測したほうがマシな状態だった。

## 初期値を直すと速くなるのか

+0.15の上振れが「無駄な作業」なら、初期値を直せば学習が速くなるはずである。試した。

`lm_head`の重みを100分の1にする。

```python
m = common.build_model()
with torch.no_grad():
    m.lm_head.weight.mul_(0.01)
```

結果。

```
init loss     : 4.1811   (ln(V) = 4.1744)
logits std    : 0.0705
max prob mean : 0.0173   (1/V = 0.0154)
```

init lossは4.174にほぼ一致した。ただしstdが0.0705残っている。**biasを縮小していないため**である。biasも±0.125の一様分布から初期化されるので、そのぶんのばらつきが残る。

biasも0にする。

```python
    m.lm_head.weight.mul_(0.01)
    m.lm_head.bias.zero_()
```

```
init loss     : 4.1742   (ln(V) = 4.1744)
logits std    : 0.0057
max prob mean : 0.0156   (1/V = 0.0154)
```

3つとも一様の値と一致した。init lossは4.1742で、ln(65) = 4.1744との差は0.0002。完全に一様な予測から始まっている。

### ところが学習は速くならなかった

| 条件 | init loss | iter 10 | iter 200 |
|---|---|---|---|
| 基準(既定初期化) | 4.3254 | **3.4012** | **2.4977** |
| weight ×0.01 | 4.1811 | 3.7209 | 2.5280 |
| weight ×0.01 + bias 0 | 4.1742 | 3.7162 | 2.5277 |

![初期値を一様にそろえた場合](/images/w3/scale0.01.png)

基準の図と見比べてほしい。始点が灰色の点線とほぼ重なり、序盤の急降下も消えている。狙いどおりの形にはなった。

それでも、**初期値を一様にそろえたほうが全区間で遅い。**

iter 10の時点で0.32、iter 200でも0.03ほど基準に負けている。「無駄な作業」だと思っていた序盤の急降下は、無駄ではなかったことになる。大きな勾配自体が学習の立ち上がりを速めていた、と解釈できる。

### biasを0にしても変わらなかった

`weight ×0.01`と`+ bias 0`の差もほとんどない(2.5280 vs 2.5277)。init lossは0.007改善したのに、学習の速さは変わらなかった。

遅くなった原因はweightの縮小のほうにあり、biasは関係なかった。weightを100分の1にすると`lm_head`の勾配も小さくなるので、出力層の学習の立ち上がりが遅れる。

### 逆方向にも壊す

では初期値を大きくしたらどうなるか。10倍にする。

```python
m.lm_head.weight.mul_(10.0)
```

```
init loss     : 13.7088   (ln(V) = 4.1744)
logits std    : 5.7321
max prob mean : 0.7097   (1/V = 0.0154)
```

init lossがln(V)の**3.3倍**になった。ただしこの数字は実際の悪さを過小評価している。lossは対数なので確率に直すと`e^-13.7 ≈ 100万分の1`。一様なら1.54%なので、**1万分の1以下**である。

max probは0.7097。何も学習していないのに、1つの文字に**71%**の確率を置いている。一様の46倍にあたる。

![初期値を10倍にした場合](/images/w3/scale10.0.png)

いわゆるホッケースティック型になった。最初の25 iterで13.7から3.45まで落ち、そこからは緩やかになる。

### 追いつかない

興味深いのはその後の挙動である。

| iter | 基準 | 初期値×10 | 差 |
|---|---|---|---|
| 200 | 2.5144 | 2.7388 | 0.224 |
| 600 | 2.2395 | 2.4658 | **0.226** |

400 iter経っても差が縮まらない。**初期値の悪さは一時的な遅れではなく、平行に遅れ続ける。**

もう1つ、この実験で分かったことがある。init lossは測るたびに大きく振れた(18.39 / 13.71)。一方でlogits stdは5.77 / 5.73と安定していた。

logitsが極端に尖っているため、「たまたま当たったか外れたか」でlossが大きく動く。**モデルの性質(std)は安定していて、データ次第の結果(loss)は不安定**という対比は、測定を設計するうえで覚えておく価値がある。

## この回の結論

**初期lossの確認は、性能を上げるためではなく異常に気づくためのものだった。**

基準の+0.15は既定初期化の素直な結果で、直しても利益がない(むしろ少し遅くなる)。一方、×10の+9.5は明らかな異常で、600 iter経っても回復しない。

閾値はこのあたりにある。

```
+0.15  既定初期化。異常ではない。直す必要なし
+9.5   異常。初期化を見直すべき
```

「ln(V)より高いから異常」ではなく、**どれくらい高いか**で判断する。この感覚を持てたのが収穫になった。

測定の設計についても1つ。`eval_iters = 20`として20バッチの平均を取っているのは、1バッチだと取れた箇所の難易度でブレるからである。Week3では0.01単位の差を比べるので、この精度が要る。

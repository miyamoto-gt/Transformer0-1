## はじめに

[前回](https://zenn.dev/) はnumpyでAttentionだけを実装し、$\sqrt{d}$ で割る理由が「候補の中で一番良かった」ではなく $\mathrm{Var}(\mathrm{score}) = d$ を1に戻す方程式の答えであることを確認した。

今回はその先。Attention単体では言語モデルにならないので、

- FFN（非線形）
- 残差接続（入力を足し戻す）
- LayerNorm（各トークンを正規化する）

を足して、215,873パラメータのGPTMiniをPyTorchで組んだ。

そして「なぜこれが要るのか」を、足す前と足した後を測って比べる形で1つずつ確認した。LayerNormをPre（ブロックの前）に置くかPost（後ろ）に置くかも比較した。

この記事は結論だけ並べても意味がないので、全部このフォーマットで書く。

1. 問い（なぜこれが要るのか）
2. 実験 `check_xxx.py`
3. 結果（表）
4. 読み方

## 効かなかったもの3つ

うまくいった話より、効くと思って入れたのに効かなかったもののほうが情報量が多かった。先に結論を置く。

| | 何に効くと思ったか | 実測 | どこ |
|---|---|---|---|
| FFN | 非線形を足せば、深く積んでも潰れなくなる | Attention単体より速く潰れた（rank 1 が深さ8→4に前倒し） | 1章 |
| Multi-Head | 複数の観点から同時に見れば精度が上がる | ヘッド1〜8でlossの幅 0.0056（1ヘッドが4ヘッドに勝った） | 4章 |
| 文脈長 | 長く見えれば予測しやすくなる | 4倍にして 0.0325、時間は2.9倍 | 5章 |

:::message
FFNが不要という意味ではない。**「潰れを止める役ではなかった」** というだけで、その役は残差接続が担っていた。効かなかったのは「入れた目的に対して」である。
:::

3つに共通するのは、どれもモデルの容量をほとんど増やしていないことだった。最後に残った `d_model` だけが 0.1876 動いた（6章）。

ただし「効かなかった」を正しく読むには、数字が読めなければならない。今回は2回、出ている数字を読み違えている（0.5章・3章）。数字は出ていたが、出ていた数字が別物だった。その記録も残す。

コード全体: https://github.com/miyamoto-gt/Transformer0-1

各章のコードは `all_src/W2/` にあり、見出しからリンクしている。結果はこの記事の表がそのまま実行出力である。

:::message
環境: PyTorch 2.14.0 / CPU。データは tiny_shakespeare（全1,115,394文字 = train 1,003,854 / val 111,540、語彙65文字）。乱数seedは各スクリプトで固定してあるので、手元で流せば同じ数字が出る。
:::

## 0. 作ったもの ― 215,873パラメータのGPTMini

### 問い

まず何を作ったのか。パラメータがどこに何個あるのかを把握しておかないと、あとで「効かなかった」ときにどこを疑えばいいか分からない。

### 実験

`check_model.py` / `check_data.py`

構成は `d_model=64, n_layer=4, n_head=4, block_size=128, vocab=65`。

x = self.tok_emb(idx) + self.pos_emb(pos)   # (B,T,d)
for blk in self.blocks:

x = self.ln_f(x)
logits = self.lm_head(x)                    # (B,T,vocab)
```

### 生成してみる

この構成を3000 iter学習させた（val 1.7880）モデルに、400文字生成させた結果を先に出しておく。

```

英単語としてはほぼ間違っているが、

- 単語の長さと母音・子音の並びが英語らしい
- 空行で場面が区切られる

という戯曲のレイアウトは再現できている。val 1.7880 は $e^{1.788} = 6.0$ なので「次の文字を65文字中6文字くらいまで絞れている」状態。文字の並びは学べても、単語の意味まではまだ届いていない。

以降は、この状態に至るまでに各部品が何をしていたかを分解していく。

### 読み方

パラメータの92%はBlockの中にある。うち FFN が 33,088 / 49,792 = 66%。Attention は 16,448 / 49,792 = 33% しかない。「Transformerの主役はAttention」という説明を読んだあとにこれを見ると意外だが、重みの数でいえばFFNのほうが倍ある。

`loss: 4.3229` と `expected (random): 4.1744` の比較が、この時点での唯一の健全性チェックになる。$\ln(65) = 4.174$ は「65文字を完全に等確率で当てずっぽうしたときのloss」だ。初期値はそこから少しずれた4.32。ここが4.17付近にあれば、少なくとも配線は間違っていない。

もしこれが 0.5 とか 10.0 だったら学習を回す前に止めるべきで、

- 極端に小さい → targetがinputと同じ（答えを見ている）
- 極端に大きい → 初期化か正規化が壊れている

を疑うことになる。学習前のlossは $\ln(\text{語彙数})$。これは覚えておく値だった。

## 0.5. Blockの中身

### 問い

Blockは Attention と FFN の2つの枝でできている。なぜ2つ要るのか。同じことをしているなら1つでいいはずだ。

### 実験

`check_ffn.py` / `check_attention.py`

両方に同じテストをかけた。系列の順番を入れ替えてから通した結果と、通してから入れ替えた結果が一致するか（position-wise）。

```python
perm = torch.randperm(T)
torch.allclose(ff(x)[:, perm], ff(x[:, perm]), atol=1e-6)
```

### 結果

| 項目 | FFN | Attention |
|---|---|---|
| shape | (2,6,32) → (2,6,32) | (2,6,32) → (2,6,32) |
| position-wise | **True** | **False** |
| causal（上三角が0） | ― | True |
| 行和が1 | ― | True |
| 非線形性（2階差分） | 0.471983 | ― |
| パラメータ数 (d=32) | 8,352 | 3,072（単一Head） |

### 読み方

この表の True / False が、2つの枝が別物である証拠になっている。

FFNが `position-wise: True` ということは、FFNは各トークンを完全に独立に処理している。6トークンあれば、同じ関数を6回別々に適用しているだけ。隣を一切見ていない。

Attentionは `False`。これは当たり前で、Attentionは他の位置を見るための仕組みだからだ。ただし `causal: True` なので、見えるのは過去と自分だけ。

つまり役割分担はこうなる。

| | 混ぜる方向 | できること |
|---|---|---|
| Attention | トークン間（横） | どの位置の情報を持ってくるか |
| FFN | 特徴次元内（縦） | 持ってきた情報をどう変形するか |

Attentionは情報を運ぶだけで、変形はしない。実際Attentionの中身は $\mathrm{softmax}(QK^\top/\sqrt{d})V$ で、$V$ の重み付き平均でしかない。平均は線形操作だ。だから何層重ねても線形のまま、というのが次の1章につながる。

### ここで1つ測り間違えていた

最初、非線形性を $f(a+b) - (f(a)+f(b))$ で測っていた。線形なら0になるはずだから、値が出ていればReLUが効いている ― そう考えた。

これは間違いだった。試しにReLUを外して同じ式を測ると、

| | $f(a+b)-f(a)-f(b)$ | 2階差分 $f(a+b)-f(a)-f(b)+f(0)$ |
|---|---|---|
| ReLUあり（本物） | 0.438974 | 0.471983 |
| ReLUなし（アフィン） | 0.198773 | **0.000000** |

ReLUを外しても 0.198773 出る。ゼロにはならない。

理由はbiasだ。FFNは線形写像ではなくアフィン写像 $f(x) = Ax + c$ で、

$$f(a+b) - f(a) - f(b) = (A(a+b)+c) - (Aa+c) - (Ab+c) = -c$$

$A$ が消えて $-c$ だけが残る。この式が測っていたのはbiasの大きさで、非線形性ではなかった。

正しくは2階差分を見る。アフィン写像なら

$$f(a+b) - f(a) - f(b) + f(0) = -c + c = 0$$

が厳密に成り立つので、0でなければ非線形と言える。表のとおりReLUなしは 0.000000、ありは 0.471983。これなら証拠になる。

この誤りは記事を書き終えてから、テストを書く過程で見つかった（7章）。3章とまったく同じ形の失敗 ― 数字は出ていたが、出ていた数字が別物だった。

:::details 中間層が4倍なのは
`FeedForward(d_model, mult=4)` で 64 → 256 → 64 と広げて戻している。一度広い空間に投げてからReLUで切ると、切り方の選択肢（どの次元を殺すか）が増える。4倍は原論文（512 → 2048）以来の慣習で、今回は検証していない。
:::

## 1. Attentionだけでは深さ8でrank 1に潰れる

### 問い

0.5章で「Attentionは重み付き平均だから線形」と書いた。ではAttentionだけを重ねると実際に何が起きるのか。そして FFN / 残差 / LayerNorm のどれが、それを救っているのか。

### 実験

`check_collapse.py`

同じ入力に対して、構成を4段階で積み上げながら24層通す。部品は `check_block.py` と同じ
`MultiHeadAttention`（`nn.Linear` の既定init + 出力proj）で、層ごとに独立した重みを持たせる。

測るのは2つ。

- `spread` … 系列内でトークンがどれだけ散らばっているか（全トークンの平均からの距離）
- `rank` … 16トークンの中に何本の独立な方向が残っているか（最大16）

### 結果

| depth | attention only | +ffn | +residual | +residual+LN |
|---|---|---|---|---|
| | spread / rank | spread / rank | spread / rank | spread / rank |
| 1 | 0.511968 / 16 | 0.112259 / 16 | 5.672686 / 16 | 5.674905 / 16 |
| 2 | 0.098201 / 16 | 0.005080 / 10 | 5.840691 / 16 | 5.809167 / 16 |
| 3 | 0.025146 / 8 | 0.000212 / 3 | 6.001820 / 16 | 5.934752 / 16 |
| 4 | 0.007474 / 4 | **0.000015 / 1** | 6.165458 / 16 | 6.093572 / 16 |
| 6 | 0.000513 / 2 | 0.000000 / 1 | 6.418238 / 16 | 6.243965 / 16 |
| 8 | **0.000020 / 1** | 0.000000 / 1 | 6.885200 / 16 | 6.477434 / 16 |
| 12 | 0.000000 / 1 | 0.000000 / 1 | 7.534212 / 16 | 6.693362 / 16 |
| 16 | 0.000000 / 1 | 0.000000 / 1 | 8.734312 / 16 | 7.102452 / 16 |
| 24 | 0.000000 / 1 | 0.000000 / 1 | **11.941788 / 16** | **7.748372 / 16** |

### 読み方

左2列の `rank=1` が、この章でいちばん重要な数字だ。

`rank=1` は「16個のトークンが、全部同じ1本のベクトルの定数倍になった」という意味。
`spread` がほぼ0であることと合わせると、**16トークンが同じ1点に潰れた**ことになる。
この状態ではどの位置も同じベクトルを見ているので、入力が何であっても同じ出力しか出せない。

Attentionだけなら**深さ8**、FFNを足すと**深さ4**で完全に潰れる。
4層モデルを作るつもりだったので、どちらにせよ残差なしでは組めない。

#### なぜ潰れるのか

Attentionの出力は $PV$ で、$P$ は行和が1・全要素が非負の**確率行列**だ。
掛けることは「トークンの平均を取る」ことに等しい。

平均を繰り返せば全員が同じ値に近づく。`spread` は 0.512 → 0.098 → 0.025 と、
1層ごとにおよそ1/5のペースで縮んでいる。
**Attentionを重ねることは、混ぜることではなく均すこと**だった。

#### FFNでは救えない

`+ffn` 列は `attention only` よりむしろ速く潰れている（depth 2 で rank 16 → 10、depth 4 で 1）。
0.5章で見たとおりFFNは位置ごとに独立なので、すでに全トークンが同じ値になっていたら、
同じ関数を通しても同じ値のままだ。非線形性はトークン間の区別を復元できない。

#### 残差が効く

`+residual` は24層でも `rank=16`。潰れていない。式で見ると理由は明快で、

$$h_{l+1} = h_l + \mathrm{Attention}(h_l)$$

$h_l$ がそのまま残る。平均化されるのは足される側だけなので、元のトークンの区別は上流からそのまま降りてくる。

残差の効果は勾配側でも確認した。`check_residual.py`

| depth | 元xとの向きの一致（残差なし） | （残差あり） |
|---|---|---|
| 1 | +0.033 | +0.980 |
| 2 | +0.139 | +0.927 |
| 3 | +0.034 | +0.852 |
| 4 | +0.040 | +0.766 |
| 5 | +0.052 | +0.678 |
| 6 | +0.050 | +0.592 |

| 8層通したあと入力に届いた勾配のノルム | |
|---|---|
| residual なし | 1.182670e-04 |
| residual あり | 2.931107e+01 |

残差なしは1層目で既に +0.033。cosine類似度が0ということは、入力ベクトルと出力ベクトルが直交している、つまり元の情報の向きが1層で消えている。残差ありは6層通しても +0.592 で、半分以上残っている。

勾配は $2.93 \times 10^{1}$ と $1.18 \times 10^{-4}$ で、約25万倍の差がある。残差なしの $10^{-4}$ は、学習率 $10^{-3}$ を掛けると更新幅が $10^{-7}$ になる。浮動小数の下の方で、実質何も学習されない。

#### LayerNormは、この深さではまだ効かない

右2列を8層まで見ると、`+residual` が 6.885、`+residual+LN` が 6.477。**差は1.06倍しかない。**
ここで打ち切ると「LayerNormは要らない」と読めてしまう。

差がつくのは深くしてからだ。

| depth | +residual | +residual+LN | 比 |
|---|---|---|---|
| 8 | 6.885 | 6.477 | 1.06倍 |
| 16 | 8.734 | 7.102 | 1.23倍 |
| 24 | 11.942 | 7.748 | **1.54倍** |

**残差はrankを守り、LayerNormはスケールを守る。** 役割が違うので両方要る。
ただしLayerNormの側は、8層では測定できるほどの差が出ない。
これは3章でもう一度、別の指標で出てくる。

## 2. 括弧の位置を変えると勾配が1億9千万分の1になる

### 問い

LayerNormをどこに置くか。書き方は2通りある。

```python
# Pre-LN : 枝に入る前に正規化する
x = x + attn(ln1(x))
x = x + ffn(ln2(x))

# Post-LN : 足してから正規化する
x = ln1(x + attn(x))
x = ln2(x + ffn(x))
```

違いは括弧の位置だけ。原論文はPost-LNで、今のGPT系はPre-LNを使う。なぜ変わったのか。

### 実験

`check_prepost.py`

`Block(d, block_size, pre_ln=True/False)` を12層積み、同じseed・同じ入力で最終出力の `std` と、入力まで届いた勾配のノルムを測る。

### 結果

| | std（1層目 → 12層目） | 入力に届いた勾配 |
|---|---|---|
| Pre-LN | 1.084 → 1.642 | **2.3246e+01** |
| Post-LN | 1.003 → 1.003 | **1.2099e-07** |

比にすると**約1億9千万倍**の差がついた。

### 読み方

Post-LNの `std 1.003 → 1.003` は、一見するといちばん良い数字に見える。12層通しても出力のスケールが完全に一定。1章で「スケールが膨らむのが問題」と書いたばかりなので、これは理想に見える。

**ここが罠だった。**

順伝播がきれいなことと、逆伝播が通ることは別の話だ。Post-LNは各層の出口でLayerNormが強制的にstdを1に揃えるので、順方向の数字は必ずきれいになる。何層積んでも1.003になる。つまり `std` を見てもPost-LNの異常は検出できない。

異常は勾配側にしか出ない。`1.2099e-07`。これは float32 の精度限界（$\approx 10^{-7}$）とほぼ同じ桁で、12層目で発生した誤差が1層目に届いた時点でノイズに埋もれていることを意味する。1層目と2層目は学習されない。

#### なぜ差がつくのか

逆伝播は連鎖律なので、層をまたぐたびにその層のヤコビアンが掛け算される。

Pre-LN では、残差の本流に一切手が入らない。

$$h_{l+1} = h_l + F(\mathrm{LN}(h_l)) \implies \frac{\partial h_{l+1}}{\partial h_l} = I + \frac{\partial F}{\partial h_l}$$

$I$ があるので、$\partial F$ 側がどれだけ小さくても勾配は最低でも1倍で素通りする。12層掛けても $1^{12} = 1$。これが `2.3e+01` の正体だ。

Post-LN では本流がLayerNormを通る。

$$h_{l+1} = \mathrm{LN}(h_l + F(h_l)) \implies \frac{\partial h_{l+1}}{\partial h_l} = \frac{\partial \mathrm{LN}}{\partial (\cdot)}\left(I + \frac{\partial F}{\partial h_l}\right)$$

$I$ の外側に $\partial \mathrm{LN}$ が掛かる。LayerNormは入力を std で割るので、勾配側ではおおよそ $1/\mathrm{std}$ 倍される。残差で膨らんだ分を毎層割り戻すため、この係数は1より小さい。仮に0.3として12層なら $0.3^{12} \approx 5 \times 10^{-7}$。実測の $10^{-7}$ と桁が合う。

掛け算が12回入るか、足し算で迂回できるか。差はそこだけだった。

#### Pre-LNの代償

Pre-LN側は `std 1.084 → 1.642` で膨らんでいる。本流を正規化しないので当然だ。だから最終ブロックの後に `ln_f` を1つ置いて、`lm_head` に渡す前に整える。

```python
x = self.ln_f(x)            # ← Pre-LN構成では必須
logits = self.lm_head(x)
```

Pre-LNは「スケールの管理を各層から出口1箇所に移す」設計だと理解した。Post-LNは毎層きれいにする代わりに勾配経路を毎層壊す。Pre-LNはその逆をやる。

## 3. stdが膨らんだのは、モデルのせいではなかった

### 問い

ここからは失敗の記録である。

1章でLayerNormがスケールを抑えることを確認したので、「LayerNormを入れれば深く積んでもstdは1付近で安定するはずだ」と考えて測りにいった。

### 最初に出ていた数字

`check_ln_need.py` は当初、その場で手書きした簡易Attentionを使っていた。

```python
Wq, Wk, Wv = (torch.randn(d, d) / d**0.5 for _ in range(3))   # 手書きinit
def attention(h):
    q, k, v = h @ Wq, h @ Wk, h @ Wv
    P = torch.softmax(q @ k.transpose(-2,-1) / d**0.5, dim=-1)
    return P @ v, P                                            # 出力projなし
```

これで12層測ると、LayerNormありでも std が 1.129 → **10.971** と10倍に膨らんだ。
LayerNormなしに至っては **3214.550**。

ところが同じ条件を本物の `Block` で測ると（`check_block.py`）、8層で **1.258** しか動かない。
手書き版の同じ8層は 6.414。**5倍違う。**

同じPre-LNのはずなので、どちらかの読み方が間違っている。

### 原因

犯人は初期化のスケールだった。

| | 手書きattention | 本物のMultiHead |
|---|---|---|
| 重みのstd | 0.1712（$1/\sqrt{d} = 0.1768$） | 0.1015（$1/\sqrt{3d} = 0.1021$） |
| 出力proj | なし | あり |
| std=1 の入力を1回通した出力std | **0.409** | **0.163** |

`torch.randn(d,d) / d**0.5` は**正規分布**なので重みのstdが $1/\sqrt{d} = 0.177$。
一方 `nn.Linear` の既定初期化は $U(-1/\sqrt{d},\ 1/\sqrt{d})$ で、
一様分布のstdは幅 $\times 1/\sqrt{12}$ なので $1/\sqrt{3d} = 0.102$。
**同じ「$\sqrt{d}$ で割る」でも、正規分布か一様分布かで1.7倍違う。**
さらに本物は出力 `proj` をもう1枚通すので、もう一段小さくなる。

結果、1層あたり本流へ足される量が 0.409 対 0.163 で**2.5倍**違う。
残差は足し算なので、この差が層数ぶん積み上がっていた。

### 実験（修正後）

`check_ln_need.py` を `check_block.py` と同じ部品にそろえた。
`MultiHeadAttention` + `nn.Linear` の既定init + 出力proj、層ごとに独立した重み。
**測りたいのはLayerNormの有無なので、それ以外は本番と同じにする。**

### 結果

| depth | std (LNなし) | 最終行P.max (LNなし) | std (LNあり) | 最終行P.max (LNあり) |
|---|---|---|---|---|
| 1 | 1.054 | 0.1345 | 1.051 | 0.1356 |
| 4 | 1.196 | 0.2065 | 1.155 | 0.1714 |
| 8 | 1.401 | 0.1276 | 1.291 | 0.1153 |
| 12 | 1.868 | 0.3820 | 1.498 | 0.1440 |
| 16 | 2.500 | 0.3698 | 1.668 | 0.1062 |
| 20 | 3.176 | 0.5227 | 1.737 | 0.1176 |
| 24 | **3.923** | **0.9401** | **1.785** | **0.1119** |

### 読み方

**結論そのものが変わった。**

修正前は「LayerNormありでも12層で10倍に膨らむ」と読んでいた。
修正後の12層は **1.498**。1.5倍しか動かない。
**10倍という数字は、Pre-LNの性質ではなく手書き初期化の性質だった。**

そして本題のほうは、深さを倍にして初めて見えた。

- **12層では差がつかない。** LNなし 1.868 / LNあり 1.498。この深さで打ち切ると「LayerNormは要らない」と読めてしまう
- **24層で分かれる。** LNなしは std 3.923・最終行P.max **0.9401**。Attentionが1箇所に張り付き、softmaxが飽和している
- LNありは 24層でも std 1.785・P.max 0.11 で安定している

$\partial P_i / \partial s_j = P_i(\delta_{ij} - P_j)$ なので、P.maxが1に近づくと勾配が0に落ちる。
**LayerNormは必要だった。ただしそれを示すには12層では足りなかった。**

### 何を間違えたか

W1の教訓をそのまま繰り返していた。

W1では「$\sqrt{d}$ で割るスケーリングは、初期化が単位分散を保っている前提とセット」だと書いた。
今回もまったく同じで、Pre-LNのstdの振る舞いは枝の初期化スケールとセットだった。
それを切り離して「Pre-LNだから膨らむ」と読んだのが誤りだった。

**検証コードに本番と違う実装を書いた時点で、測っているのは本番ではない。**

### P.max も測り違えていた

修正の途中でもう1つ見つかった。当初は `P.max()` ― 行列全体の最大値を見ていたが、
本物のAttentionには causal mask があるので**0行目は必ず `[1, 0, ..., 0]` になる**。
全体のmaxは何があっても 1.0000 に張り付き、指標として死んでいる。

手書き版にはマスクが無かったので、この問題は修正して初めて出てきた。
上の表が「最終行のP.max」なのはそのためで、全文脈が見える行だけを見ている。

### ついでに、理論値のほうも合っていない

`check_block.py` には `(sqrt予測 3.000)` という列がある。
残差を $L$ 回足せばstdは $\sqrt{L}$ で伸びる、という理論値だ。実測は 1.258。

$\sqrt{L}$ は「毎層、本流と同じ大きさの独立なベクトルを足す」という仮定から出る。
実際に足されているのは本流の 0.16 倍しかないので、そもそも前提が違う。
**理論値が合わないときは、まず理論の前提が現場で成立しているかを見る。**

## 4. Multi-Headは効かなかった

ここからは実際に学習を回す。tiny_shakespeare を3000 iter、`lr=1e-3, batch_size=32, n_layer=4` で固定し、1つずつ条件を変えて比べた。

実験スクリプト: `check_sweep.py`

### 問い

Multi-Head Attentionは「複数の観点から同時に見る」仕組みとして説明される。ヘッドを増やせば表現力が上がるはずだ。実際いくつが最適なのか。

### 実験

`d_model=64, block_size=128` を固定し、`n_head` だけ 1 / 4 / 8 と変える。

```python
self.head_size = d_model // n_head      # 64/1=64, 64/4=16, 64/8=8
q = q.view(B, T, nh, hs).transpose(1, 2)
```

`qkv` も `proj` も shape が `n_head` に依存しないので、3つとも同じ 215,873 パラメータになる。純粋にヘッドの分割数だけの比較になっている。

### 結果

| n_head | head_size | params | train | validation | 時間 |
|---|---|---|---|---|---|
| 1 | 64 | 215,873 | 1.6046 | **1.7840** | 94s |
| 4 | 16 | 215,873 | 1.6117 | 1.7880 | 135s |
| 8 | 8 | 215,873 | 1.5967 | **1.7824** | 196s |

最良と最悪の差は **0.0056**。

### 読み方

`n_head=1` が `n_head=4` に勝っている。

これが今回いちばん予想と違った。単一ヘッドの 1.7840 は、4ヘッドの 1.7880 より良い。`n_head=8` が 1.7824 で最良だが、1ヘッドとの差は 0.0016 で、代わりに時間が2.1倍かかっている。

差 0.0056 をどう読むか。lossは対数なので、差は比に直すと意味が分かる。

$$e^{0.0056} = 1.0056$$

つまり「次の文字の予測確率が 0.56% 変わった」程度。一方この記事の1章では、残差の有無で勾配が25万倍変わっていた。Multi-Headは、この構成では測定できるほどの効果を持っていない。

#### なぜ効かないのか

`d_model=64` を4分割すると `head_size=16` になる。W1で見たとおりAttentionのスコアは $\sqrt{d_k}$ でスケールされ、$d_k = 16$ では内積を取る空間が狭い。8ヘッドなら `head_size=8` でさらに狭い。

分割できるだけの容量が元からなかった、というのが素直な読み方だと思う。原論文は `d_model=512, n_head=8` で `head_size=64`。今回の `head_size=16` は、その1/4しかない。

もうひとつ、タスクが簡単すぎる可能性もある。文字単位のShakespeareで次の1文字を当てる問題は、「複数の観点を同時に見る」必要がある場面がそもそも少ないのかもしれない。

#### 正しい読み方は「効かなかった」で止めること

ここで「Multi-Headは無意味だ」と結論すると間違える。この実験が言えるのは「`d_model=64` / 4層 / 文字単位Shakespeare / 3000 iter では差が出ない」までだ。

効果がないことを示したのではなく、**効果を測れる条件になっていなかった。** 差 0.0056 は、seedを変えたときのばらつきに埋もれる大きさでもある。

:::message
以降は `n_head=4` を基準にする。8が最良だったが差0.0016に対して時間が1.5倍かかるので、他の条件を比較する土台としては割に合わない。
:::

## 5. 文脈長を4倍にしても0.033しか下がらない

### 問い

Multi-Headが効かないなら、次は何を増やすか。**文脈長（`block_size`）** は素直な候補に見える。長く見えれば予測しやすくなるはずだ。

### 実験

`n_head=4, d_model=64` を固定し、`block_size` を 32 → 128 に4倍する。

### 結果

| block_size | params | train | validation | 時間 |
|---|---|---|---|---|
| 32 | 209,729 | 1.6421 | 1.8205 | 46s |
| 128 | 215,873 | 1.6117 | **1.7880** | 135s |
| 差 | +6,144 | −0.0304 | **−0.0325** | 2.9倍 |

### 読み方

4倍にして 0.0325。比に直すと $e^{0.0325} = 1.033$ で3.3%。その代わり時間は2.9倍になっている。

パラメータは 6,144 しか増えていない。増えたのは `pos_emb` だけで、$(128-32) \times 64 = 6{,}144$。文脈長はほぼタダで伸ばせるが、計算時間には効く。Attentionのスコア行列が $T \times T$ なので、$T$ を4倍にすると16倍になるためだ。

#### なぜ伸びないのか

素直な解釈は、**文字単位の予測に必要な文脈がもともと短い**ということ。

英語の文字予測では、直前の数文字でほとんど決まる。`t h` と来たら次は `e` が濃厚で、128文字前の情報は要らない。`block_size=32` でも「単語1〜5個ぶん」は見えていて、その先を足しても当てられる文字がほとんど増えない。

#### ここで効く読み方

0.0325 という数字そのものより、「何を増やしたのに効かなかったか」のほうが情報量が多い。

4章と5章で分かったのは、

| 増やしたもの | パラメータ | validation改善 |
|---|---|---|
| ヘッド数（1 → 8） | ±0 | 0.0056 |
| 文脈長（32 → 128） | +6,144 | 0.0325 |

どちらも「重みをほとんど増やさずに構造だけ変える」変更で、どちらも効かなかった。共通点がここにある。

## 6. 残った候補はd_modelだけ

### 問い

4章と5章で潰れたのは、モデルの容量を増やさない変更だった。ならば残る候補は、容量そのもの ― `d_model` になる。

### 実験

`n_head=4, block_size=128` を固定し、`d_model` を 64 → 128 に倍にする。

### 結果

| d_model | params | train | validation | train/valの差 | 時間 |
|---|---|---|---|---|---|
| 64 | 215,873 | 1.6117 | 1.7880 | 0.1763 | 135s |
| 128 | 824,897 | 1.3714 | **1.6004** | 0.2290 | 226s |
| 差 | 3.8倍 | −0.2403 | **−0.1876** | +0.0527 | 1.7倍 |

全5実験を並べる。

| 変えたもの | params | validation | 基準との差 |
|---|---|---|---|
| `n_head=1` | 215,873 | 1.7840 | −0.0040 |
| `n_head=4`（基準） | 215,873 | 1.7880 | ― |
| `n_head=8` | 215,873 | 1.7824 | −0.0056 |
| `block_size=32` | 209,729 | 1.8205 | +0.0325 |
| `d_model=128` | 824,897 | **1.6004** | **−0.1876** |

### 読み方

`d_model` だけが桁違いに効いている。

文脈長4倍が 0.0325 なのに対し、`d_model` 2倍は 0.1876。5.8倍の差だ。4章・5章で「効かない」を2回引いたあとにこれを見ると、この構成のボトルネックは一貫して容量だったと読める。

#### ただし、ここには罠がある

`train/valの差` の列を見る。0.1763 → 0.2290 に開いている。

trainは 1.6117 → 1.3714（−0.2403）下がったのに、validationは 1.7880 → 1.6004（−0.1876）しか下がっていない。下がり幅の差 0.0527 は、**訓練データの暗記に使われた分と、train/val の分布そのものの違いの合計**である。

後者を無視できないのは、valが原文の後ろ約10%を切っただけのものだからだ。train とは別の戯曲が入っていて、登場人物名も語彙分布も違う可能性がある。その分は暗記ではない。切り分けるなら、trainの中から未使用の区間をもう1つのvalとして測ればいいが、今回はやっていない。

いずれにせよvalidationが下がっているので現時点ではまだ得だ。ただしこのまま `d_model` を増やし続ければ、どこかでvalidationが下がらなくなり、やがて上がり始める。「`d_model` を増やせばよい」は、この範囲でしか正しくない。

#### d_model が効く理由

`d_model` は、1トークンを表すベクトルの長さそのものだ。これを増やすと、

- **Attention**: `head_size` が 16 → 32 になり、スコアを取る空間が広がる（4章の制約が緩む）
- **FFN**: 中間層が 256 → 512 になり、非線形変換の自由度が上がる
- **残差ストリーム**: 層から層へ運べる情報の本数が増える

4章でMulti-Headが効かなかったのも、`head_size` が狭かったからだったと考えると、5つの実験が1つの話につながる。`d_model=128` で `n_head` を振り直せば、今度は差が出るかもしれない。これは次回の宿題にする。

## 7. checkとtestは別物だった

### 問い

`check_*.py` を10本書いた時点で「確認は足りている」と思っていた。W1にはテストがあるのに、W2には書いていなかった。要るのか。

### 実験

`tests/test_w2.py`

19本書いたうえで、わざとコードを壊して落ちるかを確かめた。**テストが通ることには意味がなく、壊したときに落ちることに意味がある。**

```bash
pytest tests/test_w2.py -q     # 19 passed
```

### 結果

| わざと入れたバグ | 落ちたテスト |
|---|---|
| causal maskを外す | 4本 |
| Pre-LN / Post-LNを取り違える | 1本 |
| LayerNormで sqrt を忘れる | 2本 |
| FFNのReLUを外す | 1本 |
| $\sqrt{d_k}$ のスケーリングを忘れる | 1本 |
| 残差接続を外す | 1本 |
| gamma と beta を入れ替える | 4本 |

### 読み方

この表を作る過程で、0.5章の測り間違いが見つかった。

「FFNのReLUを外す」を入れたとき、最初のテストは19本全部通ってしまった。$f(a+b) - (f(a)+f(b))$ で非線形性を測っていたので、ReLUがなくても値が出ていたためだ。2階差分に直して、ようやく落ちるようになった。

#### checkとtestの役割は違う

| | `check_*.py` | `tests/test_w2.py` |
|---|---|---|
| 出力 | 数字 | pass / fail |
| 読むのは | 人間 | 機械 |
| 問い | 「どう振る舞うか」 | 「壊れていないか」 |
| 失敗の形 | 数字を読み違える | 落ちる |

`check_*.py` は数字を出すが、判定はしない。判定を人間がやるので、3章でも0.5章でも読み違えた。テストは判定まで機械がやるので、読み違えようがない。

#### いちばん要るのは causal のテスト

7つのバグのうち、**causal maskを外すのは自力では絶対に気づけない。**

未来が見えるようになると、モデルは答えを見ながら答えを書けるのでlossは下がる。むしろよく下がる。`check_model.py` も `check_sweep.py` も「良くなった」と表示する。生成文だけが妙に下手なままになる。

**数字が良くなる方向に壊れるバグは、数字を見ても見つからない。** これがW2でテストを書くべき最大の理由だった。

### 学んだこと

**1. 各部品には別々の失敗モードが対応している**

| 部品 | 外すとどう壊れるか |
|---|---|
| FFN | 非線形が入らない（が、潰れは止まらない） |
| 残差 | rankが1に潰れ、勾配が消える |
| LayerNorm | stdが発散し、softmaxが飽和する |
| Pre-LN配置 | 順伝播は正常に見えたまま、勾配だけ死ぬ |

「なぜ要るのか」は、外して壊れ方を見るのがいちばん速かった。

**2. 順伝播がきれいでも安心できない**

2章のPost-LNは `std 1.003 → 1.003` という、いちばんきれいな数字を出した。壊れていたのは勾配側だけだった。順伝播の指標だけを見ていると、Post-LNの異常は永久に検出できない。

**3. 数字が読めないと実装は失敗する**

これが今回の主題だった。同じ形の失敗を2回している。

| どこで | 出ていた数字 | 実際に測っていたもの |
|---|---|---|
| 3章 | std が10倍に膨らむ | 検証コードの初期化スケール |
| 0.5章 | $f(a+b)-f(a)-f(b) = 0.438974$ | biasの大きさ（非線形性ではない） |

どちらも数字は出ていた。出ていた数字が別物だった。`check_*.py` は数字を出すだけで判定しないので、この種の失敗を止められない。7章のテストは、0.5章の誤りを実際に見つけて直させた。

比較したい対象以外を揃えていなければ、測っているのは別物である。W1で「$\sqrt{d}$ は初期化の前提とセット」と書いたのに、同じ間違いを繰り返した。

**4. 効かなかった実験のほうが情報量が多い**

4章と5章は、どちらも「効かなかった」で終わっている。しかしその2つがあったから、6章の `d_model` が「残った唯一の候補」として意味を持った。最初から `d_model` を振っていたら、「大きくすれば良くなる」以上のことは分からなかった。

### 次回

次週は「壊して観察する」がテーマになっている。意図して壊すなら、意図しない破壊と区別できる必要がある。`test_w2.py` が19本通る状態を基準線にして、そこから何本落ちたかで「何を壊したか」が言えるようにしておく。

- `test_w2.py` の19本を基準線にして「壊して観察する」
- `d_model=128` で `n_head` を振り直す（4章の仮説の検証）
- 学習率とwarmupを入れる
- train/val の差が開き始める点を探す

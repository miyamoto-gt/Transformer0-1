## はじめに

[前回](https://zenn.dev/)は、壊す前に「正常とは何か」を数値で定義した。4つの物差しを用意し、基準となるモデルを固定した。

```
 4.174  ln(V)        何も知らない
 3.30   ユニグラム    文字の頻度のみ覚えた
 2.24   基準の到達点  文脈依存の規則を学んでいる
```

今回から実際に壊す。扱うのは3つである。

| 壊し方 | 何を変えるか |
|---|---|
| #1 学習率過大 | `lr` を100倍・1000倍 |
| #2 targetsシャッフル | 正解ラベルの対応を壊す |
| #5 residual削除 | `x + attn(...)` を `x = attn(...)` に |

**この3つ、最終的にほぼ同じ場所に着地した。** 学習曲線を並べても区別がつかない。原因はまったく別なのに、である。

どうやって切り分けたかが今回の主題になる。

## #1 学習率を100倍にする

まず素直なバグから。学習率を`1e-3`から`1e-1`にする。100倍である。

```python
common.run(m, tag="lr1e-1", lr_override=1e-1)
```

初期値はいじっていないので、init lossは基準と同一の4.3254。**壊したのは学習率だけ**だと確認できる。

![学習率0.1](/images/w3/lr1e-1.png)

| iter | val loss |
|---|---|
| 100 | 3.0872 |
| **175** | **2.9313** ← 底 |
| 300 | 2.9897 |
| 400 | 3.0245 |
| 600 | 2.9645 |

iter 175で底を打ち、そこから上昇に転じた。以降は2.9〜3.03のあいだで揺れるだけで、下がらない。

### これは危険な形である

もしiter 175で学習を止めていたら、「2.93まで下がった。学習できている」と判断していた。そこまでの曲線は正常に見える。

**lossが下がっていることと、下がり続けていることは別**である。終盤の傾きを見なければ気づけない。

原因は、学習率が大きすぎて最小値を通り越していることにある。坂道を下るのに歩幅が大きすぎて、谷底を跨いで反対側の斜面に着地している状態。往復しているので、それ以上進めない。

## さらに1000倍にする

`lr = 1.0`にする。基準の1000倍である。

![学習率1.0](/images/w3/lr1.0.png)

こちらは一目で異常だった。

| iter | val loss |
|---|---|
| 25 | **210.00** |
| 125 | 56.59 |
| **250** | **215.52** ← ピーク |
| 400 | 33.24 |
| 500 | 6.24 |
| 600 | **3.3410** |

iter 25で210まで跳ね上がり、250で215のピーク。lossが200ということは、正解の文字に`e^-200`の確率しか置いていない。事実上ゼロである。

### NaNにはならなかった

「発散といえばNaN」と思っていたので、これは意外だった。

理由はAdamWにある。Adamは勾配を`√(勾配の二乗の移動平均)`で割るので、**1回の更新幅が学習率でほぼ頭打ち**になる。SGDなら無限大に飛んでいくところが、Adamだと「大きく飛ぶが有限」に収まる。

**振動もまた発散の形**だった。

### さらに意外だったこと

iter 250をピークに、そこから**下がり続ける**。そして600 iterでは3.3410。

この3.34という値は、前回定義した**ユニグラム水準(3.30)** にあたる。暴走した末に、「文字の出現頻度だけを覚えた状態」へ落ち着いた。

暴走で重みが大きくなりすぎた結果、文脈を使う能力は失われたものの、出力層のバイアスだけは頻度を学び直せた、という解釈ができる。

### 打ち切る位置で結論が変わる

ここで重要なことに気づいた。

| 打ち切り位置 | 読み取れること |
|---|---|
| 200 iter | 「60〜180のあいだで振動している」 |
| 600 iter | 「暴走した後、ユニグラム水準へ復帰した」 |

同じ実験でも、どこで止めるかで結論が変わる。この話は第3回でもっと極端な形で出てくる。

## #2 正解ラベルの対応を壊す

次はデータ側のバグである。

言語モデルの学習では、入力`x`と正解`y`が1文字ずれた同じ文章になっている。

```
x: '\nANGELO:\nAnd she wil'
y:  'ANGELO:\nAnd she will'
```

位置tでは`x[0..t]`を見て`y[t]`を当てる。この対応をバッチ内でシャッフルする。

```python
x, y = get_batch(train, block_size, batch_size)
y = y[torch.randperm(y.size(0))]     # y の行だけ入れ替える
```

実際に何が起きるか、デコードして確認した。

```
正常     : x '\nANGELO:\nAnd she wil'  →  y 'ANGELO:\nAnd she will'
シャッフル: x '\nANGELO:\nAnd she wil'  →  y 't know it.\n\nCORIOLAN'
```

ANGELOのセリフを見せて「次はCORIOLANUSの台詞だ」と教えている状態である。

### 結果

![targetsシャッフル](/images/w3/shuffle_y.png)

| iter | val loss |
|---|---|
| 50 | 3.3616 |
| 200 | 3.3384 |
| 400 | 3.3389 |
| 600 | 3.3403 |

iter 50で3.36に到達した後、**550 iterのあいだ小数第2位まで動かない**。基準は同じ区間で2.86から2.24まで下がっている。

止まった位置がユニグラム水準である。対応が壊れていても`y`の中身はシェイクスピアの文章のままなので、**文字の出現頻度という情報だけは生き残る**。それを出力層のバイアスが拾い、3.3で頭打ちになる。

### エラーは一切出ない

このバグの厄介さはここにある。

- コードは正常に動く
- lossも計算される
- ln(V)より下まで下がる
- 学習も進んでいるように見える

ただ何も学べていないだけである。3.34という値も、それ単体を見れば異常だと分からない。前回ユニグラム水準を用意していなければ、「まあこんなものか」で済ませていた可能性がある。

実際のコードでも、`y`のシフトを忘れる、データローダで対応がずれる、複数ファイルを読むときに順序が食い違う、といった形で起こりえる。

## #5 残差接続を削除する

3つ目は構造のバグである。

Blockの中身はこうなっている(Pre-LN)。

```python
x = x + attn(ln1(x))
x = x + ffn(ln2(x))
```

この`x +`を消す。

```python
x = attn(ln1(x))
x = ffn(ln2(x))
```

前回のコードは書き換えず、クラスを継承して`forward`だけ上書きした。

```python
class BlockNoResidual(Block):
    def forward(self, x):
        a, _, _ = self.attn(self.ln1(x))
        x = a                          # x + a ではない
        x = self.ffn(self.ln2(x))      # x + ffn(...) ではない
        return x
```

モデルを作った後、Blockのクラスを差し替える。

```python
m = common.build_model()
for i in range(len(m.blocks)):
    m.blocks[i].__class__ = BlockNoResidual
```

重みはそのままで`forward`の実装だけ変わるので、初期値を揃えた比較ができる。

### 残差は何をしているのか

実験の前に整理しておく。`x`は「その位置についてモデルが現時点で持っている理解」である。層を通るたびに更新される。

```python
x = x + attn(ln1(x))
    ↑         ↑
    素通り    加工された分
```

残差があると経路が2本ある。加工せずそのまま通る道と、attentionで加工された道。**各層は「何を付け加えるか」だけを担当**し、これまでの理解は保たれる。

消すと、`x`はattentionの出力で置き換えられる。attentionは重み付き平均なので、通すたびに位置固有の情報が薄まる。各層が毎回ゼロから作り直すことになる。

ノートにたとえると、**追記か書き直しか**の違いである。

私の予想は「4層と浅いので影響は小さい」だった。深いモデルでこそ効く仕組みだという理解だったからである。

### 結果

![残差削除](/images/w3/no_residual.png)

| iter | val loss |
|---|---|
| 25 | 3.3747 |
| 200 | 3.3513 |
| 400 | 3.3663 |
| 600 | 3.3432 |

予想は外れた。**4層でも致命的**である。iter 25でユニグラム水準に到達し、そこから600 iterまで一切動かない。

失われたのは文脈依存の規則(3.30 → 2.24の区間)である。文字の頻度は出力層のバイアスが担当するので、そこまでは到達する。

## 本題:この3つが区別できない

ここで問題が起きた。

| 実験 | iter 600 |
|---|---|
| #1 lr=1.0 | 3.3410 |
| #2 シャッフル | 3.3403 |
| #5 残差削除 | 3.3432 |

**小数第2位まで同じである。**

#2と#5のグラフを見比べてほしい。上に貼った2枚である。どちらもiter 25付近で3.37に達し、以降フラット。trainとvalが重なったまま。私には区別できなかった。

原因はまったく違う。

- **#2**:データの対応が壊れている。モデルは正常
- **#5**:モデルの構造が壊れている。データは正常

それでも症状が同じになる。「症状 → 原因」の表を作るつもりだったのに、1つの症状に複数の原因が対応してしまった。

## 切り分ける方法1:データを目視する

一番安い方法から。`x`と`y`をデコードして目で見る。

```python
x, y = get_batch(train, block_size, batch_size)
print(repr("".join(itos[i.item()] for i in x[0][:20])))
print(repr("".join(itos[i.item()] for i in y[0][:20])))
```

正常なら1文字ずれた同じ文章が出る。#2なら無関係な2つの文章が並ぶ。**1秒で判定できる。**

`repr()`で囲むのは、改行を`\n`として見えるようにするためである。

これで#2かどうかは即座に分かる。対応が正常なら、原因はモデル側にある。

## 切り分ける方法2:層別の勾配ノルム

次に安い方法である。Blockごとに勾配の大きさを測る。

```python
def block_grad_norm(b):
    sq = sum(p.grad.pow(2).sum() for p in b.parameters() if p.grad is not None)
    return sq.sqrt().item()
```

1 iterだけ回して比較した。

| 条件 | block0 | block1 | block2 | block3 | 形 |
|---|---|---|---|---|---|
| 基準 | 0.3706 | 0.3622 | 0.3702 | 0.3749 | 均一 |
| #2 シャッフル | 0.3547 | 0.3504 | 0.3622 | 0.3657 | **均一** |
| **#5 残差削除** | 1.8481 | 3.2803 | 4.2306 | **5.2668** | **階段状** |

きれいに分かれた。

**基準と#2は4層とも0.35〜0.37で揃っている。** 残差が勾配の素通り経路を作るためである。足し算の微分は1なので、どの層にもほぼ同じ大きさの勾配が届く。#2はモデル構造が正常なので、この形になる。

**#5だけが階段状になった。** 出力側に向かって約1.8倍ずつ増えている。逆伝播は出力側(block3)から入力側(block0)へ流れるので、**層を通るたびに増幅されている**ことが分かる。

これで判別表ができた。

```
loss が 3.3 で停滞している
  │
  ├─ 1. x と y を目視              ← 1秒
  │     対応が壊れている → #2
  │     正常 → 次へ
  │
  ├─ 2. 層別の勾配ノルムを測る
  │     階段状 → #5
  │     均一   → 次へ
  │
  └─ 3. 学習曲線の全体を見る
        途中で暴走していた → #1
```

**原則は安いものから。** データの目視は1秒、勾配の測定は数秒、内部の観察は実装が要る。

## 勾配が大きいのに学習できない

#5の結果で、もう1つ予想を外した。

残差を消すと勾配消失が起きると思っていたが、**実際は勾配爆発**だった。基準の5〜14倍である。

そして奇妙なことに、勾配がこれだけ大きいのに学習は止まっている。矛盾しているようだが、説明はつく。

**AdamWは勾配の大きさを正規化する。** 勾配を`√(二乗の移動平均)`で割るので、大きさ自体は吸収される。それでも学習できないということは、**問題は勾配ではない**ということになる。

原因は順方向にある。各層が`x`を置き換えるので、情報が積み上がらない。attentionは重み付き平均なので、通すたびに位置固有の情報が薄まる。4回繰り返せば、位置ごとの違いはほぼ消える。

**勾配の異常は原因ではなく目印**だった。切り分けには使えるが、それ自体が学習を止めているわけではない。

## まとめ

今回の3つで分かったこと。

**1. 症状が同じでも原因は別々。** #1(lr=1.0)、#2、#5はすべて3.3で停滞する。曲線では区別できない。

**2. 切り分けには追加の測定が要る。** データの目視と層別の勾配ノルム、2つの道具で3つを分離できた。

**3. 安い順に試す。** 1秒で済む確認から始める。実装が必要な観察は最後になる。

**4. 打ち切る位置で結論が変わる。** #1のlr=1.0は、200 iterでは「振動」、600 iterでは「暴走後に復帰」と読みが変わった。

**5. 予想は当たらない。** 「4層なら残差は要らない」も「残差を消すと勾配消失」も外れた。測らないと分からない。
